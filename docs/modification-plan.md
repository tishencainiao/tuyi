# 途忆修改方案（v1.0.0 → v2.0.0）

> 针对用户反馈的 7 个问题，把「补丁式修 bug」升级为「按主题、按版本的增量演进」。
> 本文只出方案与取舍，不写代码；所有改动仍遵守既有纪律：每版一提交一 tag、双远端同步、data/ 与 .env 不进库。

---

## 0. 结论先行（一页读完）

- **7 个问题归并为 6 个主题**：多轮会话 / 记忆时序准确 / 用户体系 / 看板定位 / 记忆可编辑 / 地图点亮。
- **版本节奏（按目标，不按日期）**：
  - `v1.1.0 身份与多轮会话`：本地账号 + 历史加载（地基，先做）
  - `v1.2.0 记忆准确与可控`：行程时序去歧义 + 对话式记忆编辑（创新点深化，答辩重点）
  - `v1.3.0 个人看板`：看板从「全体画像」改为「个人画像 + 全局匿名聚合」（大数据元素落位）
  - `v2.0.0 地图点亮`：全国地图按省/市点亮（展示亮点，最后做）
- **取舍原则**：这是毕设，不是商业产品。凡「横切面大、对论文无增益、演示用不上」的一律不做（第三方登录、找回密码、县级地图、多端云同步等）。

## 2. 逐主题方案

### 主题 A　多轮会话与历史（问题 ①）

**现状根因（已核对代码）**：`data/memory/<userId>.json` 里的 `turns` 已有 `ts/role/text`，但
1. 没有「会话（conversationId）」概念，40 条 turns 是一条平铺时间线；
2. `/api/profile` 只回 `turnsCount`，**不返回 turns 内容**，也没有任何「读历史」接口；
3. 前端 `index.html/app.js` 进入即空，从不请求历史。

**选项**

| 选项 | 做法 | 评价 |
|---|---|---|
| A1 前端缓存 | 把当前对话存 localStorage，刷新恢复 | 最小，但只解决「同浏览器切页」，与后端已有 turns 重复存储、易不同步，换设备/清缓存即丢 |
| **A2 会话 + 历史接口（推荐）** | turns 加 `conversationId`；新增 `GET /api/history?userId=&conversationId=`；前端进入拉最近会话并加载 | 彻底解决，且为 B（时序）和 C（登录）打地基 |
| A3 完整多会话管理 | 分页/搜索/重命名/删除/导出 | 商业级，毕设用不上，不做 |

**推荐 A2，分两步**：第一步先做「单会话历史加载」（把当前 userId 的 turns 当一条时间线拉回来，最小可用）；第二步再引入「会话列表 + 新建/切换」。第一步即可让问题 ① 消失。

**影响面**：`brain/memory.js`（turns 加 conversationId、`appendTurn` 签名）、`server.js`（新接口）、`brain/agent.js`（`runAgent` 贯穿 conversationId）、`web/app.js` + `index.html`（加载与渲染历史）。

**工作量**：小–中（接口 + 数据结构 + 前端三处，横切但不深）。

**风险**：现有 turns 无 conversationId，需在 `load()` 里给旧数据回填默认会话；历史是静态渲染、实时是 SSE 逐字流式，渲染逻辑要分开；40 条上限对跨多轮历史偏少，可考虑按「每会话保留 N 条」而非总量 40。

### 主题 B　记忆准确性与行程时序（问题 ②）

**现状根因（已核对代码）**：`appendItinerary` **已经存了 `ts`**（`memory.js` 第 115 行），数据侧时序是有的——问题出在 `renderBlock`（第 154–174 行）**只注入 `insights` 和检索到的 `memories`，完全不注入 `itineraries`**。模型不知道用户去过几次、第几次是哪里，只能凭感觉回答，于是「第一次」答成「上次」。

**选项**

| 选项 | 做法 | 评价 |
|---|---|---|
| **B1 注入行程时间线（推荐）** | `renderBlock` 把 itineraries 按 `ts` 排序、标序号（第 1 次、第 2 次…，含目的地/日期/天数/预算），注入 system；同时在 `persona.md` 加一条「用户用序数词指代行程时必须按时间线回答，回答前先复述你理解的是哪次」 | 直击根因、工作量小；恰好是论文「防幻觉」的优质案例 |
| B2 检索增强 | 把 itineraries 也纳入 `retrieve()` 按关键词检索 | 更精细，但「第一次/上次」这类序数语义，关键词检索命中不稳 |
| B3 结构化日期字段（可选增强） | 行程加「旅行日期」字段，支持「去年夏天」「今年五一」这类相对时间 | 体验更好，但需用户额外提供，可放到后面 |

**推荐 B1 为主，B3 作可选增强**。B1 是「数据 + 注入 + 提示工程」三管齐下，正好对应论文「解决幻觉」的落点，答辩可讲。

**影响面**：`brain/memory.js`（`renderBlock` 注入行程、可选给 itinerary 加 date）、`brain/prompts/persona.md`（去歧义指令）、测试 smoke/live、`docs/ablation.md` 结论。

**工作量**：小（几处改动）。

**风险**：itineraries 最多 20 条、每条含 10 天行程，全注入会撑爆 system prompt——需只注入摘要（目的地/日期/天数/预算），不注入逐日明细；`memory.js` 第 172 行「以本次说法为准」的兜底要保留，避免记忆冲突反噬。

### 主题 C　用户体系与数据归属（问题 ③ + ④ 的一半）

**现状根因（已核对代码）**：`/api/chat` 的 userId 来自 `body`（可伪造）；`/api/profile?userId=` 任何人可查他人数据（无鉴权）；`/api/stats` 全量；前端 localStorage 随机 u-xxx。数据即 `data/memory/<userId>.json` 文件。

**选项**

| 选项 | 做法 | 评价 |
|---|---|---|
| C1 轻量通行码 | 输入昵称 → 服务端生成 userId + token，存 httpOnly cookie，无密码 | 最小，独立演示友好，但不跨设备 |
| **C2 本地账号（推荐）** | 注册（用户名+密码）→ 登录 → session（随机 token + httpOnly cookie）→ 登出 → 鉴权中间件；密码用 Node 原生 `crypto.scrypt` 加盐哈希；账号表存 `data/users.json` | 演示「完整用户体系」，不依赖外网，代码可理解 |
| C3 第三方 OAuth | 微信/GitHub 登录 | 需申请应用、回调域名、公网可达，本地演示要隧道，配置复杂，**不做** |

**推荐 C2，且只做「注册 / 登录 / 登出 / 鉴权」四件事**，不做找回密码、验证码、邮箱（论文展望可提一句 C3）。

**影响面（全项目最横切的一处）**：新增 `brain/auth.js`；`server.js` 所有 `/api/*`（除 `/api/health`）加鉴权中间件；前端三页从 localStorage 的 u-xxx 改为读 session cookie，新增登录/注册视图；userId 由服务端从 session 解析，**不再信任 body**。

**工作量**：中（横切面广，但每处都不深）。

**风险**：改动面最大、最易漏（所有接口 + 三页 + 测试都要动）；已有 u-xxx 数据需归属（可提供「游客数据导入新账号」，或毕设阶段直接清空演示环境重来）；密码安全责任——哈希不落明文、data/ 已 gitignore、README 说明；session 选纯内存（重启即失效）还是落盘 JSON（简单、够用，推荐）。

### 主题 D　看板定位：个人 vs 全局（问题 ④⑤）

**现状根因（已核对代码）**：`/api/stats` 固定走 `stats.computeStats(stats.collectRecords())` 全量扫描，无 userId 维度；看板四图（标签/目的地/预算/意图）天然是「全体画像」；而用户要的是「我去过哪些城市、几次」这类**个人旅行画像**。

**选项**

| 选项 | 做法 | 评价 |
|---|---|---|
| **D1 个人为主 + 全局次页签（推荐）** | 新增 `stats.computeUserStats(record)`；`/api/stats?userId=`（鉴权后从 session 取）返回个人统计：去过城市+次数（从 `itineraries.destination` 精确统计）、预算/意图分布、行程次数；「全体用户」聚合降级为可选的全局次页签（匿名聚合） | 既满足用户视角，又保住论文「大数据元素」 |
| D2 看板保持全局 + 个人中心强化 | 只改 profile 页 | 小，但不解决「定位」问题，仍是管理员视角 |
| D3 砍掉全局 | 只留个人 | 不推荐——「用户偏好统计」是论文硬要求，需保留聚合能力 |

**推荐 D1**。关键改进：**「去过城市次数」改为从 `itineraries.destination` 结构化统计**（现状 `stats.js` 第 111–123 行是「从记忆文本 `text.includes(city)` 猜 + itinerary.destination 混算」，城市名还是硬编码 `CITIES` 表）。个人视角应优先用 itinerary.destination（结构化、准确），`CITIES` 表退化为别名/兜底映射。

**影响面**：`brain/stats.js`（新增 computeUserStats + 城市统计口径）、`server.js`（/api/stats 鉴权 + userId）、`web/dashboard.html/dashboard.js`（个人视角 + 全局次页签）、`scripts/seed-demo.js`（演示数据隔离）。

**工作量**：中。

**风险**：统计口径变更会改变现有数字，需同步改 smoke 断言；全局聚合含演示数据会「污染」，需在 UI 标注「全局（含演示数据）」或把演示数据隔离到单独目录。

### 主题 E　记忆可编辑与可控（问题 ⑥）

**现状根因（已核对代码）**：`memories` 已有稳定 `id`（`memory.js` 第 98 行），但**没有任何编辑/删除接口**；前端 profile 只读；更关键的是 `tools.dispatch(name, args)`（`tools.js` 第 24–36 行）**不传 userId/上下文**，agent 无法通过工具改「当前用户」的记忆——这是做「对话式记忆编辑」的架构缺口。

**选项**

| 选项 | 做法 | 评价 |
|---|---|---|
| E1 个人中心 CRUD | 加 `PUT/DELETE /api/memory/:id`（鉴权 + userId 校验），前端编辑/删除按钮 | 小，解决「可改」，但只能手动 |
| **E2 CRUD + 对话式工具（推荐）** | E1 + 新增 `tools/memory-edit.js`（工具 `memory_edit`，参数 `{action: add|update|remove, id?, text?, tags?}`），agent 识别「记住我喜欢海边」「删掉不吃辣那条」并调用；**先给 `tools.dispatch` 加可选 context、`runAgent` 传 `{userId}`** | 把记忆从「只读黑盒」变「可干预」，答辩亮点 |
| E3 完整记忆管理系统 | 版本回滚 + 冲突合并 + 审计 | 过度设计，不做 |

**推荐 E2**。呼应创新点「记忆消化」的可解释性，且工具化符合现有 tools 自动加载架构。

**影响面**：`brain/tools.js`（dispatch 加可选第三参 context，向后兼容）、`brain/agent.js`（runAgent 传 userId）、新增 `tools/memory-edit.js`、`brain/memory.js`（新增 updateMemory/removeMemory 按 id 定位）、`server.js`（CRUD 接口 + 鉴权）、`brain/prompts/persona.md`（何时用 memory_edit）、`web/profile.html/profile.js`（编辑/删除 UI）、测试。

**工作量**：中。

**风险**：agent 误改记忆——需加权限边界（建议只允许改/删 memories，`insights` 是 digest 产物默认只读或需单独确认；`remove` 必须给出可定位的 id/text）；dispatch 加 context 要向后兼容（现有 `run(args)` 不受影响，新工具可接收 `(args, context)`）。

## 5. 先做什么 / 后做什么 / 不做什么

**先做（地基 + 低风险 + 高增益）**
1. C 本地账号（最小版）——不做的后果是所有后续都建在「可伪造 userId」的沙子上。

**后做（依赖前置）**
4. E 记忆编辑（依赖 C，且要改 dispatch 横切）。
5. D 个人看板（依赖 C）。
6. F 地图点亮（依赖 C + D 的「城市次数」数据）。

- 完整多会话管理（搜索/重命名/导出/分页）。
- 县级地图粒度、实时 GPS 轨迹、足迹打卡社交。
- 记忆版本回滚、冲突合并、审计日志。
- 云存储、多端实时同步。
- 商业级账号体系（角色权限分级、风控）。

## 6. 专项评估

### 6.1 登录系统（本地账号 vs 第三方 vs 轻量 session）

| 维度 | C1 轻量 session | **C2 本地账号（推荐）** | C3 第三方 OAuth |
|---|---|---|---|
| 有无密码 | 无 | 有（scrypt 加盐哈希） | 平台代管 |
| 依赖外网 | 否 | 否 | 是（回调域名/公网可达） |
| 独立演示友好度 | 高 | 高 | 低（要隧道） |
| 代码可理解度 | 高 | 中（session + 哈希） | 中（协议复杂） |
| 演示「完整用户体系」 | 弱 | 强 | 强但受制平台 |
| 工作量 | 小 | 中 | 中–大 |
| 结论 | 时间紧的兜底 | **主推** | 不做 |

**落地要点（C2 最小版）**：
- 密码哈希用 Node 原生 `crypto.scrypt`（零依赖，不用引 npm）。
- 登录成功后签发随机 token，存 `httpOnly` cookie（前端 JS 拿不到，防 XSS 冒用）。
- 鉴权中间件从 cookie 解析 session → 得到 userId → 供 `/api/chat` `/api/history` `/api/stats` `/api/profile` `/api/memory` 使用，**不再信任 body 的 userId**。
- session 落盘 `data/sessions.json`（重启不失效），`data/users.json` 存用户名→哈希+盐+userId。
- 脱敏红线沿用：密码哈希、session、用户数据都在 `data/`，已被 `.gitignore` 与 pre-commit 钩子挡住。

### 6.2 全国地图点亮

**① 地图数据来源（ECharts 5 无内置中国地图）**

| 来源 | 做法 | 评价 |
|---|---|---|
| **阿里 DataV.GeoAtlas（推荐）** | 下载全国 GeoJSON 本地 vendor 到 `web/vendor/`：省级 `100000.json`、省市县级 `100000_full.json` | 免费、无需 key、离线可演示；数据源自高德，与项目已用高德一致，论文注明来源与授权 |
| 高德行政区划 API | 运行时调接口取边界 | 需 Web 服务权限、运行时联网，不稳，不推荐 |
| 运行时 CDN | 页面加载时远程拉 GeoJSON | 离线演示会挂，不推荐 |

**② 省市粒度**

| 粒度 | 数量 | 评价 |
|---|---|---|
| 省级 | 34 | 最简，只「点亮去过的省」 |
| **市级（推荐）** | ~330 地级市 | 精确到「去过哪些城市」，与 D 的「城市次数」完美联动（颜色深浅=次数）；`100000_full.json` 约几 MB，本地 vendor 可接受 |
| 县级 | 数千 | 数据大、标记负担重，不做 |

**③ 数据从哪来（点亮依据）**

| 方式 | 做法 | 评价 |
|---|---|---|
| 自动 | 从 `itineraries.destination` 匹配城市名 → 自动点亮 | 省事，与 D 联动 |
| 手动 | 用户点选城市标记「去过」（问题 ⑦「用户可自行设置」） | 记录未通过 app 的出行，存 `visitedCities: [{name, province, count, manual}]` |
| **混合（推荐）** | 自动 + 手动 + 可取消 | 兼顾「真实记录」与「用户自主」 |

**工作量**：下载 GeoJSON + ECharts `map` series 渲染 = 小；后端 visitedCities 存储/接口 + 与 itinerary 联动 = 中；前端地图页 + 点选交互 + 省市缩放 = 中–大。整体定为 v2.0.0。

**风险**：
- GeoJSON 体积（全国市级 full 几 MB），需确认不进 .gitignore 或说明来源，README 注明。
- 城市名匹配（`itinerary.destination` 是自由文本，如「北京」vs「北京市」vs「帝都」），需别名/归一化，可复用 `stats.js` 的 `CITIES` 表 + 手动映射。
- 坐标偏移：**只用「城市/省名 → GeoJSON 的 name 字段」匹配点亮，不做经纬度描点**，即可完全避开 GCJ-02 偏移问题。
- 数据授权：DataV.GeoAtlas 供学习/演示，论文注明来源与用途。

## 7. 取舍理由（为什么这样分、为什么不堆功能）

1. **先修地基，再谈体验**：登录（C）是所有「当前用户」语义的前提，历史（A）依赖稳定身份；跳过它们直接做看板/地图，等于在可伪造 userId 上盖楼。
2. **把「补丁」转成「论文素材」**：问题 ② 不是简单修 bug，而是论文「解决幻觉」的现成案例；问题 ⑥ 让「记忆消化」从黑盒变可解释；问题 ④⑤ 正好把「大数据元素」讲清楚边界。**每一处改动都要能写进论文，否则降级或不做。**
3. **每版一个目标、一提交一 tag**：与既有版本纪律一致，避免「攒一堆一起改」导致测试和文档对不上。
4. **横切面最小化**：dispatch 加 context、鉴权中间件这类横切改动只做一次、向后兼容，避免反复返工。
5. **明确不做什么**：第三方登录、县级地图、完整多会话管理等「横切大、论文无增益、演示用不上」的功能一律砍掉——毕设的时间价值在「把创新点讲透」，不在「堆功能像不像产品」。
