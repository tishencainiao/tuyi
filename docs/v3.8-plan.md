> 编写依据：已逐条核对的代码现状（文中行号均为当前代码实际行号）

## 0. 版本划分建议

| 方案 | 内容 | 评价 |
| --- | --- | --- |
| 方案一：单版本 | v3.8.0 一次做全部四条 | 一次提交改动过大（后端 3 个文件 + 前端 4~5 个文件 + 新增组件），测试面广，出错后定位难，不推荐 |
| **方案二：两版本（★推荐）** | **v3.8.0 = ① + ③ + ④；v3.9.0 = ②** | 见下 |
| 方案三：三版本 | v3.8.0 = ①，v3.9.0 = ③④，v3.10.0 = ② | ① 单独成版 tag 价值低；且 ① 的 PlanCard/ChatPage 改动与 ③④ 对同一批文件的改动重叠，拆开要两次回归 |

**推荐理由（方案二）**：

- ①③④ 同属一条主线——「行程的状态治理与对话归属」，改的是同一批文件（tools/plan-trip.js、brain/memory.js、web/src/pages/ChatPage.tsx、web/src/components/PlanCard.tsx、brain/prompts/persona.md），合并开发只回归一次；
- ③④ 本来就互相依赖（行程卡按对话过滤依赖 conversationId 字段，见第 3 节），必须同版；
- ② 是独立的引导体验（新组件 + 资料字段 + 个人中心开关），适合单独一版评审 UI；
- 每版都可独立验收、独立打 tag、双远端（gitee/github）推送，符合项目版本纪律。

> 备选：如果用户想尽快把 ① 修掉，也可以拆一个 v3.8.0 = ① 先行发布（改动 <30 行、风险极低），③④ 顺延为 v3.9.0，② 为 v3.10.0。默认仍按方案二。

## 1. 需求①：已完成的行程不能直接修改，必须退回状态再改

### 1.1 现状核对（已核实）

- `tools/plan-trip.js:83-100`：mode=update 时只校验 plan 存在且属于当前用户（`memory.getPlan`），**不校验 status**，completed 也能直接改；
- `brain/memory.js:200-233`：`upsertItinerary` 的 update 分支同样不校验 status（落库层不拦，只改数据）；
- `brain/memory.js:36-41`：`STATUS_FLOW` 已全连通，completed 可回退到 draft/confirmed/in_progress；`setItineraryStatus`（`brain/memory.js:267-283`）校验合法流转；
- `tools/update-plan-status.js:27-31`：**已核实 status enum 含 `draft`**（`['draft','confirmed','in_progress','completed']`），回退到草稿无需改工具定义；
- `web/src/components/PlanCard.tsx:97-140`：只要传了 onRevise 就显示「在这基础上修改」（:101-105）；**completed 卡目前显示：「在这基础上修改」「回退状态」（:121-125，非 draft 都显示）「改名」，但没有专属的「退回修改」入口**——注意：并非"没有任何操作按钮"，问题在于无效的修改按钮仍显示、退回入口不显眼；
- `web/src/pages/ChatPage.tsx:338-345`：对所有行程卡都传了 onRevise；`web/src/pages/ProfilePage.tsx:423-430` 只传 onStatus/onDelete/onRename（个人中心无修改按钮，不受影响）；
- `brain/prompts/persona.md:39-45`：生命周期第 5 条「已确认行程不能删除」，**没有**「completed 不能直接改、要先退回」的规则。

### 1.2 方案选项

**方案 A：仅后端拦截**

- 改哪些：`tools/plan-trip.js:83-100` update 分支加校验——`plan.status === 'completed'` 时返回 `{ok:false, error:'这份行程已完成，不能直接修改；请先和用户确认是否退回（update_plan_status 退回 draft/in_progress），退回后再修改'}`；双保险：`brain/memory.js:200-233` upsertItinerary update 分支加同样拦截。
- 影响哪些功能：工具层/落库层生效，小忆调用 plan_trip(update) 会收到错误并转述给用户。
- 代价：极低（约 10 行）。
- 风险：前端「在这基础上修改」按钮仍在——用户点击后提示语发出去、小忆再报错绕一圈，体验差；错误提示靠 LLM 转述，可能表达不准。

**方案 B：后端拦截 + 前端配合**

- 后端同 A；前端 `web/src/components/PlanCard.tsx`：
  - :101 改为 `onRevise && status !== 'completed'`——completed 卡不再显示「在这基础上修改」；
  - completed 卡把「回退状态」升级为专属主按钮「退回修改」（`type="primary"`，点击直接打开回退 Modal，目标状态**默认 draft**，回退成功提示「已退回草稿，可以修改了」；Modal 里仍可选 confirmed/in_progress）。
- 影响哪些功能：用户操作路径变为「退回修改 → 修改」，清晰闭环；draft/confirmed/in_progress 卡的按钮不变。
- 代价：小（PlanCard 单文件，约 20 行）。
- 风险：状态机按钮条件变多，需回归四种状态的全部按钮。

**方案 C：B + persona 规则（★推荐）**

- 在 B 基础上，`brain/prompts/persona.md`「行程的生命周期」增加第 6 条：
  > 6. **已完成的行程（completed）不能直接修改**。用户想改已完成行程时，先征得用户同意，调用 `update_plan_status` 退回（一般退回 draft，也可以退回 in_progress 表示行程继续），再调 `plan_trip(mode:"update")` 修改；用户没同意退回前不要改。
- 影响哪些功能：小忆在对话里主动引导——「这份行程已经完成，要改的话我先帮你退回草稿？」
- 代价：极小（改 prompt 文本）。
- 风险：LLM 遵循率不是 100%，所以 A 的后端拦截必须保留作为硬底线，C 只负责体验层。

### 1.3 推荐与理由

**★方案 C（= A + B + C 全做）。** A 是硬保证（任何路径都无法直接改 completed，包括未来新入口），B 让前端不给无效按钮、给正确入口，C 让对话引导与界面一致。三层合计约 30 行改动，没有理由只做一层。

### 1.4 验证方法

1. 后端：造一份 completed 行程，调 `plan_trip(mode:'update', plan_id)` → 返回 `ok:false` 且 error 含「已完成」；用 `update_plan_status` 退回 draft 后再 update → 成功；
2. 前端：completed 卡不显示「在这基础上修改」，显示「退回修改」；点击 → 回退 Modal 默认 draft → 确认后卡片变草稿，重新出现「确认行程」「在这基础上修改」；
3. 状态回归：draft/confirmed/in_progress 卡的全部按钮行为与 v3.7 一致（确认/出发/结束/回退/删除/改名）；
4. persona：清空对话后对小忆说「帮我改一下那份已完成的柳州行程」，小忆应回复类似「它已完成，要不要我先帮你退回草稿再改」，而不是直接调用 update；
5. 回归个人中心（ProfilePage 无修改按钮，行为不变）与相册页（若有行程展示）。

## 2. 需求③：对话顺序错乱（旧行程卡压在新消息上方）

### 2.1 现状核对（已核实）

- `web/src/pages/ChatPage.tsx:105`：`Promise.all([api.history('default',60), api.plans()])`——**api.plans() 返回该用户全部行程**；
- `ChatPage.tsx:122-145`：timeline 把 messages + plans 合并后按 `ts` 字符串升序排序；行程卡用 `plan.ts`（服务端创建时间，`brain/memory.js:237`），消息用客户端 `new Date().toISOString()`（ChatPage.tsx:217）；
- `brain/memory.js:229-230`：**update 时会刷新 `target.updatedAt`，但 `ts` 不变** → 前端按 ts 排序时，修改后的卡片不会挪到最新位置；
- 根因：行程卡没有「归属对话 + 最新活动时间」参与时间线，历史行程（如旧柳州方案）永远留在时间线上，用户新发「柳州方案」消息后旧卡排在消息上方。

### 2.2 方案选项

**方案 A：只改排序键（不引入 conversationId）**

- 改哪些：`ChatPage.tsx:135-143` 排序时行程卡改用 `plan.updatedAt || plan.ts` 参与比较。
- 影响哪些功能：修改后的卡片会挪到时间线最新处。
- 代价：极低（几行）。
- 风险：不根治——历史行程仍出现在每个对话里；与 ④ 合并做时这行排序反正要一起改，属于过渡补丁，不单独推荐。

**方案 B：conversationId 过滤 + updatedAt 排序（★推荐，与 ④ 一起做）**

- 数据：itinerary 新增 `conversationId` 字段（创建时写当前对话 id；旧数据缺失视为 `'default'`，惰性迁移，见第 5 节）；
- 后端：`brain/memory.js` 的 `upsertItinerary` 接收 `options.conversationId`（`brain/agent.js:117` 已把 conversationId 传入 tools.dispatch 的 context，`tools/plan-trip.js` 的 `run(args, context)` 里取 `context.conversationId` 回传即可）；`listPlans` 返回 conversationId；
- 前端：ChatPage 只保留 `conversationId === 当前对话` 的行程卡；timeline 排序：行程卡用 `updatedAt || ts`，消息用 `ts`；
- 影响哪些功能：③④ 一起解决；个人中心/相册页仍显示全部行程，不受影响；
- 代价：中等（清单见第 3 节）；
- 风险：客户端与服务端时钟不一致时，消息与卡片的相对位置可能差几秒（本地单机开发可忽略）；旧数据依赖惰性默认。

### 2.3 验证方法

1. 用 v3.7 的数据启动新版 → 旧行程出现在 'default' 对话，位置不变；
2. 对话 A 让小忆生成「柳州方案」→ 卡片出现在对话 A；切到对话 B → 看不到柳州卡；
3. 在对话 A 修改柳州行程 → 卡片按 updatedAt 挪到该对话时间线最新处；
4. 发一条新消息 → 消息与卡片按时间正确交错，不再出现「新消息被旧卡片挤到上方」。

## 3. 需求④：新开对话（一个对话 = 一个旅途）

### 3.1 现状核对（已核实）

- 后端已支持 conversationId：`brain/memory.js:101-118` turns 带 conversationId（默认 'default'），`getHistory` 按对话过滤（:113-118）；`server.js:331` `/api/chat` 接受 body.conversationId；`server.js:357-368` `/api/history` 接受 query；`brain/agent.js:47-52` 开轮注入最近 20 轮也按对话过滤；`brain/agent.js:117` tools.dispatch 传入 `{userId, conversationId}`；
- **行程没有 conversationId**：`data/memory/<userId>.json` 的 itineraries 只有 id/ts/createdAt/updatedAt/status/title/destination/budget_cny/days/previousDays/revisions（`brain/memory.js:235-245`），`upsertItinerary` 不记录对话；
- 前端 `ChatPage.tsx:105、:238` 写死 'default'；
- 没有对话列表 API 和前端 UI；对话没有标题；
- 小忆的记忆注入是全局的：`brain/memory.js:448-460` `renderBlock` 的【行程时间线】取全部非 draft 行程，不分对话；
- 细节：`brain/memory.js:294` `removeItinerary` 删除时补的记事 turn 写死 `'default'`，多对话后需改为该行程的 conversationId。

### 3.2 方案选项

**方案 A（MVP，★推荐）：对话列表从 turns 派生，顶部下拉切换**

- 后端新增 `GET /api/conversations`（`server.js`，约 30 行）：扫描该用户 turns，按 conversationId 分组 → `[{id, title, lastTs, count}]`，按 lastTs 倒序；`title` = 该对话第一条 user 消息截断 12 字；'default' 恒在（无消息时 title 为「默认对话」）。**无新存储、零迁移**；
- 前端 `ChatPage.tsx`（约 80 行）：
  - 顶部加一条工具条：对话下拉（antd Select）+「新对话」按钮；
  - 「新对话」：`crypto.randomUUID()` 生成新 id → 切换（清空本地 messages/plans）→ 发出第一条消息后该对话才出现在列表（title=首条消息）；
  - 当前对话 id 存 localStorage（如 `tuyi.conversationId`），刷新后恢复；
  - 切换对话：重新请求 `api.history(current, 60)` + `api.plans()` 并只保留 `conversationId === current` 的行程卡；`:238` 改为 `chatStream(text, current, {...})`；
  - 新组件：无（复用 antd Select）。
- 影响哪些功能：仅聊天页 + 一个 API；个人中心/相册不变；**小忆的全局记忆与【行程时间线】注入保持不变（跨对话共享是卖点）**；
- 代价：中等；
- 风险：`MAX_TURNS=120`（`brain/memory.js:21`）按总量裁剪后，老对话的首条 user 消息可能被裁掉 → 标题兜底「未命名对话」；未发消息就切走的新对话不在列表里（可接受，MVP 边界）。

**方案 B：对话实体落库（支持改名/删除）**

- 新增 conversations 存储（id/title/createdAt/lastTs 每条一条），POST /api/conversations 新建、GET 列表、PATCH 改名、DELETE 删除；前端加改名/删除入口。
- 优点：标题永久保存、空对话可保留、支持重命名/删除。
- 代价：多一套 CRUD + 存储 + 前端入口，工作量约为 A 的 1.5~2 倍。
- 风险：与 turns 双写一致性（每条 turn 都要维护 lastTs/标题）。
- 定位：MVP 用 A；将来做「重命名/删除/归档对话」时升级到 B。

**方案 C：左侧对话列表（ChatGPT 式布局）**

- 在 A/B 基础上改整页布局为左侧栏。UI 改动大、移动端需抽屉化，对本科生工作量不友好。暂不推荐，可作 v4.x 美化项。

### 3.3 特别说明（必须与 ③ 一起做）

- 行程卡新增 conversationId 并做旧数据迁移（见 2.2 方案 B），否则「新对话」只是消息分开、卡片还是全局大杂烩，④ 等于没做；
- **保留全局注入**：`renderBlock` 的【行程时间线】（`brain/memory.js:448-460`）继续全局，小忆跨对话记得你去过哪、喜欢什么——这是分层记忆的卖点；只让**聊天时间线里的行程卡**按对话过滤；
- `removeItinerary` 的记事 turn（`brain/memory.js:294`）改用该行程的 `conversationId || 'default'`。

### 3.4 MVP 边界（本版不做，记入 backlog）

对话重命名、删除、归档、置顶；空对话保留；对话数上限；多端同步。

### 3.5 验证方法

1. 老用户数据：无 conversationId 的 turns 自动归 'default'，旧对话内容完整显示；
2. 新建对话 → 发「帮我规划柳州3日游」→ 列表出现标题「帮我规划柳州3日游」（截断后），消息都在该对话；
3. 在该对话生成行程 → 卡片只在该对话出现；切回 'default' → 看不到该卡；
4. 刷新页面 → 停留在刚才的对话（localStorage）；
5. 两个对话各聊几句 → 来回切换消息/卡片互不串；对话 B 里小忆仍记得对话 A 提过的偏好（全局记忆注入不变）；
6. 删除草稿 → 记事提示出现在该行程所属对话，而非都串到 'default'。

## 4. 需求②：简易模式（新对话小忆先教用法 + 旅行意向表）

### 4.1 现状核对（已核实）

- 已有注册后引导页 `/onboarding`（个人资料表单可跳过），个人中心有资料编辑；
- 聊天页空态（`ChatPage.tsx:298-313`）已有欢迎语 + `SUGGESTIONS` 静态 Tag（:35-40），点击只把文案填入输入框；
- `brain/profile.js:20` `FIELDS` 列表可扩展；`updateProfile(userId, patch)`（:118）按 FIELDS 过滤字段；资料存 `data/user-profile/<userId>.json`；
- 前端 `api.profile()`（`web/src/api.ts:249`，GET /api/profile）可拿到资料；
- 没有「新对话时小忆先教用法」「填旅行意向表自动发起对话」「简易模式开关」。

### 4.2 方案选项

**方案 A：纯前端静态引导（★推荐）**

- **simple_mode 字段**：`brain/profile.js:20` FIELDS 加 `'simple_mode'`（布尔）；`getProfile` 读旧文件时缺失默认 `true`（符合「默认为简易模式」，老用户自动 true）；
- **聊天页空态改造**（`ChatPage.tsx:298-313`，simple_mode=true 时显示引导卡）：
  - 小忆教学卡（静态文案，三块）：「你可以和我说」——帮我排一次柳州3日游 / 查天气 / 改行程；「我能给你」——路线+景点+天气+预算、记住你的偏好、管理行程状态；「第一次用？点快速开始填个表，我直接帮你排」；
  - 「快速开始」按钮 → 新组件 `web/src/components/QuickStartModal.tsx`：表单字段**全部可跳过**——目的地、出发日期、玩几天、预算、同行人、兴趣偏好；提交后把已填字段拼成一条消息（例：「帮我规划一次旅行：目的地柳州，2026-12-01 出发，玩 3 天，预算 2000 元，2 人同行，喜欢美食和拍照」）直接走 `send()`；
  - 空态底部保留 SUGGESTIONS chips + 「先跳过，直接聊」入口；
- **个人中心开关**：`ProfilePage.tsx` 加「简易模式」Switch，`PUT /api/userinfo`（`web/src/api.ts:233`）保存 `simple_mode`；关闭后聊天页空态回到 v3.7 的简单欢迎语；
- 影响哪些功能：聊天页空态 + 一个新 Modal 组件 + 个人中心一个开关 + profile.js 一个字段；
- 代价：中等（前端约 150 行 + 后端字段 1 行）；
- 风险：教学文案是静态的，需人工维护，且**文案承诺的能力必须是小忆真实具备的**（对照 persona.md 工具清单撰写，避免教用户说它不会做的事）；表单以后若升级为结构化工具参数需重构，MVP 拼消息即可。

**方案 B：后端 LLM 生成教学语**

- 新对话首条（或 /teach 指令）由小忆即兴教学。
- 代价：每轮多耗 token；内容每次不稳定，可能承诺做不到的功能。
- 定位：可作 A 的后续增强（把 A 的教学卡文案交给 LLM 润色），MVP 不推荐。

**方案 C：独立向导页**

- 新建对话后跳转独立向导页（类似 /onboarding），填完回聊天页自动发送。
- 代价：多一个页面 + 路由 + 状态传递；与「对话即界面」的气质割裂，流程更长。MVP 不推荐。

### 4.3 推荐与理由

**★方案 A。** 零 token、100% 可控、复用现有 Modal/表单/资料体系；B 不稳定费钱，C 流程绕。教学卡文案建议与 `brain/prompts/persona.md` 的「工具使用」「行程生命周期」能力清单逐条对照后撰写。

### 4.4 验证方法

1. 新用户（无 simple_mode 字段）进聊天页 → 显示教学卡 + 快速开始；老用户同样默认 true；
2. 填表（部分字段留空）提交 → 自动发出一条包含已填字段的消息，小忆正常回复并调用工具；整表留空跳过 → 正常手动输入；
3. 个人中心关闭简易模式 → 聊天页空态变回简单欢迎语；重新打开 → 恢复教学卡；
4. `/onboarding` 注册引导流程不受影响；simple_mode 持久化（重启服务后仍在）。
